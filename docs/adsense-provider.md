# The AdSense revenue provider (#4)

How Forepay proves a creator's trailing AdSense revenue with Reclaim zkFetch, what ends up
in the signed claim, and what a consumer of that claim **must** check. Code:
`be/src/adsense/`. Run: `pnpm -C be prove:adsense`.

---

## One request, to the AdSense Management API

```
GET https://adsense.googleapis.com/v2/accounts/{pub-id}/reports:generate
    ?dateRange=CUSTOM
    &startDate.year=…&startDate.month=…&startDate.day=…
    &endDate.year=…&endDate.month=…&endDate.day=…
    &metrics=ESTIMATED_EARNINGS&currencyCode=USD&reportingTimeZone=ACCOUNT_TIME_ZONE
Authorization: Bearer <OAuth token, scope adsense.readonly>   ← secret header, not in the claim
```

**Why the API and not the AdSense web UI.** The API returns a documented JSON `ReportResult`
and authenticates with one read-only bearer token, which zkFetch sends inside the TLS
session and leaves out of the claim. The web UI is an obfuscated app behind a full Google
session cookie. Matching it would be fragile, and that cookie can do far more than read a
report.

**Window: the last 3 complete calendar months**, counted 2 days after month end (a month
that has ended in UTC may not have ended in the account's time zone, and reporting lags).
Calendar months, not "last 90 days", so that every proof made in the same period has the
same window. That matters for the nullifier, below.

**What the attestor sees of the response.** Four regexes are both matched and revealed:
the column currency is `USD`, `startDate` and `endDate` equal the requested window, and
`totals` holds one decimal value, captured as `revenueUsd`. Everything else in the
response (account name, rows, averages) stays hidden.

## The signed claim, field by field

| Field | Content | Why it is safe |
| --- | --- | --- |
| `provider` | `"http"` | Constant |
| `parameters.url` | the URL above | The publisher id is public: it appears in the ad code on every page that shows AdSense ads |
| `parameters.method`, `.body` | `GET`, `""` | Constants |
| `parameters.headers` | `accept`, zkFetch's `User-Agent` | Public headers only. The audit refuses any other header |
| `parameters.responseMatches` / `.responseRedactions` | the four regexes | Patterns, not data |
| `context.contextAddress` | borrower's `G…` address | Public. **This is the #17 binding**: it sits inside the signed bytes |
| `context.contextMessage` | `forepay:adsense-trailing-revenue:v1` | Constant purpose string |
| `context.extractedParameters.revenueUsd` | e.g. `"1234.56"` | The figure being proven. Disclosed on purpose |
| `context.providerHash` | 32-byte hash | Derived from the public parameters |
| `owner` | 20-byte address | The zkFetch client key's address. Public |
| `timestampS`, `epoch` | integers | When it was attested, and the attestor epoch |

The live claim's own table, generated by the audit, is posted on #4.

`auditRevenueProof` enforces this as an **allow-list**: an unknown key anywhere fails,
even if it looks harmless. It also scans the whole proof for anything shaped like a
Google credential (`ya29.`, `1//`, `GOCSPX-`, `AIza…`, `Authorization`, `Bearer`,
`cookie`), and for the exact token used. A proof that fails is never written to disk.

## What the contract must check (input to #6 and #9)

The attestor signs **whatever the fetched server returned**. A valid signature proves only
that the claim's bytes were attested, not that they came from Google. So:

1. **Pin the URL, or the claim proves nothing.** An attacker can run zkFetch against
   `https://attacker.example/…` returning `"totals": … "value": "9999999"` and get a
   perfectly valid signature. The contract must accept only claims whose `parameters` are
   exactly this provider's template.
   *Recommendation:* the relay submits `pub-id`, the window and the context fields; the
   **contract rebuilds `parameters` from the template itself** and hashes that, never
   trusting a submitted `parameters` string. It then needs no JSON parsing, and a forged
   URL cannot be submitted at all. The exact template bytes come from the first live
   proof (#5).
2. **Nullifier = hash(`pub-id`, window), not the proof identifier.** Re-proving the same
   account for the same window gives a *new* identifier (the timestamp differs). A nullifier
   keyed on the identifier would let one month's revenue fund an advance per re-proof.
3. **Borrower = `contextAddress`**, read from the signed context, never from a parameter
   beside it (#9, #18). Also check `contextMessage` equals the constant.
4. **Freshness from `timestampS`**, against ledger time, with a bound #6 sets in seconds.
5. **`revenueUsd` is a decimal string.** Parse it into fixed-point (e.g. cents, rejecting
   more than 2 decimals) before sizing. The regex admits only `\d+(\.\d+)?`.

## Where zkFetch runs

- **Gate (#5):** the Node CLI, run by the account owner on their own machine with their
  own token (backend mode, `RECLAIM_APP_SECRET` local).
- **Product (#17):** in the creator's browser, in zkFetch's *frontend mode*. The backend
  issues a short-lived session signature restricted to
  `https://adsense.googleapis.com/v2/accounts/*`, and the Google token never reaches a
  Forepay server. That is the product's whole premise: no credentials shared.

## Open points

- **License.** `@reclaimprotocol/zk-fetch` is **AGPL-3.0**. Fine for an open-source repo
  that is itself AGPL-compatible, but this repository has no license yet. Choose one
  (AGPL-3.0 is the simple fit) or get Reclaim's permission before anything closed-source
  uses it.
- **Estimated vs finalised earnings.** AdSense finalises a month early in the next month.
  A proof made in the first days of a month may carry the previous month's estimate. If
  #6 wants finalised figures only, raise `SETTLE_DAYS`.
- **OAuth app.** `adsense.readonly` is a sensitive scope. An unverified Google OAuth app in
  *Testing* mode allows up to 100 listed test users, which is enough for the demo. For the
  gate, the OAuth 2.0 Playground issues a token with no app at all.
- **`re2` is not installed** (its install script is refused). zkFetch falls back to native
  `RegExp` on the client. The attestor evaluates matches server-side with RE2, so the
  regexes avoid lookarounds and backreferences, and a test enforces that.
